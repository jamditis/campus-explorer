# Viewer architecture

How the browser viewer is put together, and the contract its modules follow. Read this before you change `app.js`, `look.js` or anything in `viewer/`.

## Rules

- No build step. Plain ES modules. Libraries are vendored in `vendor/` and resolved by the import map in `index.html`. No CDN, no bundler, no npm dependency at run time.
- One campus, one scene. The viewer loads every tile listed in `models/main/manifest.json` into a single world. There is no scene switch. The export merges the source `.blend` files (see "One campus" below).
- `models/` is generated. The viewer reads it and never changes it.
- Modules in `viewer/` that do pure maths or data work must not import `three`, so `node --test` can run them without a browser.
- Anything the viewer infers instead of reading from the model or from a cited source is labelled UNVERIFIED in the interface.
- Interface text is sentence case, plain words.

## Coordinates

| Frame | Axes | Notes |
|---|---|---|
| Blender (model) | +X east, +Y grid north, +Z up, metres | `(E - E0, N - N0) * 1200/3937` from EPSG:6527 (NAD83(2011) / New Jersey, US survey feet). Origin `E0 = 575880`, `N0 = 738340` ftUS. Z is NAVD88 metres. |
| three.js (viewer) | +X east, +Y up, **-Z grid north** | glTF export maps Blender `(x, y, z)` to `(x, z, -y)`. |

Every tile uses the same origin, whichever Blender file it came from. Grid north is about 0.2° east of true north on campus; `viewer/geo.js` has the exact value. Compass bearings in the interface are degrees clockwise from true north.

## The `app` object

`app.js` builds one object and passes it to every module factory (`createHud(app)` and so on). Modules talk to each other only through it.

```js
app = {
  THREE, renderer, scene, camera, canvas,
  controls,          // OrbitControls; enabled only in orbit mode
  look,              // see look.js
  world,             // see viewer/world.js
  input,             // see viewer/input.js
  player,            // see viewer/player.js. player.guide = { x, z, look } makes walk mode glide to (x, z) (follow me)
  follow,            // viewer/follow.js: { start(), stop(), active }
  route,             // viewer/route.js: { go(place, { stepFree }), clear(), current, graph }
  places,            // array from viewer/places.json, limited to places a tile covers (set before the `places` event)
  rooms, roomPlaces, // viewer/rooms.json parsed ({ volumes, rooms }), and its rooms as places (kind `room`); set before `places`
  state,             // { mode: 'orbit'|'fly'|'walk', view: 'first'|'third', ready, complete }
  bounds,            // THREE.Box3 around the campus tiles
  home,              // Vector3 (x, z) where the first view is centred
  sun, time,         // { azimuth, elevation } in degrees (true north), and { date, preset }
  setTime(date), resetTime(),
  on(type, fn), off(type, fn), emit(type, detail),
  invalidate(),      // ask for a redraw; the loop draws only when something changed
  setMode(mode), setView(view),
  flyTo(pose, opts), // pose = { position: Vector3, target: Vector3 }; resolves true, or false if interrupted.
                     //   opts.land: on arrival, once the tiles there are in, re-set the height (see "Moving to a place")
  placePose(place, from), // the pose a move to a place starts from: along the heading, or 'southwest' (the tour)
  landing,           // the promise of the landing step while it runs, else null
  limit,             // the flight limit { x0, x1, z0, z1, y1 } (see "Flight limit"), null before the manifest
  renderPlain(camera, target), // draw the whole campus with another camera into a render target (minimap); undoes view culling for it
  goToPlace(place),  // fly to a place from places.json; emits `place`. A room: glide to its floor, then walk there
  overview(), topView(),
  isIdle(),          // true when the camera has been still for a moment
  focus(out),        // point of interest: orbit target, or the camera position in fly and walk
  heading(),         // camera bearing, degrees clockwise from true north
  toast(text),       // short status message
}
```

### Events

| Event | Detail | When |
|---|---|---|
| `frame` | `{ dt, time }` | Every animation frame, before drawing. Keep handlers cheap. |
| `camera` | none | The camera pose changed since the last frame. |
| `fly` | `{ by }` | A module asked for a camera move (`app.flyTo`, or a jump to a share link). `by` is the asking module's name or null. The tour stops on a move that is not its own. |
| `drawn` | none | A frame was drawn. |
| `scene:start` | `{ manifest, focus, base }` | The campus began loading. |
| `places` | none | `app.places` is ready. |
| `progress` | `{ loaded, total, tiles, count, first }` | Download progress in bytes and tiles. |
| `scene:ready` | none | The first tiles are in and the view is interactive. |
| `tile` | `{ tile }` | One tile was added to the scene. |
| `scene:complete` | none | Every tile is in. |
| `mode` | `{ mode, view }` | Navigation mode or walking view changed. |
| `sun` | `{ azimuth, elevation, date }` | The sun moved. |
| `resize` | `{ width, height }` | The canvas size changed. |
| `place` | `{ place }` | The view is going to a place. |
| `player:status` | `{ text }` | Walk mode status line (empty string clears it). |
| `stats` | `{ fps, triangles, scale }` | Once a second. |
| `toast` | `{ text }` | A short message for the user. |
| `cinema` | `{ running }` | Film mode started or stopped. |
| `route` | `{ route, place, stepFree }` or null | Walking directions were set or cleared (viewer/route.js). |

### Drawing on demand

The loop does not draw when nothing changed, with one exception: the idle tree sway (see "Tree sway") redraws a
still view 14 times a second (8 on the lite profile) for 2 minutes after the last input. If a module changes something visible that is not the camera (adds a mesh, moves a marker), it calls `app.invalidate()`. `app.invalidate(true)` is the lazy form for changes that can wait a moment, such as a tile that arrived: on a slow GPU the redraw is put off for a few frame times so that loading is not held up by drawing. DOM overlays do not need it.

## `world`

```js
world.tiles                      // [{ file, center: [x, z] | null, bytes, state, root }]
world.raycast(origin, dir, far, { builtOnly, bigOnly })  // -> { point, normal, distance, object } | null. World space. Solid meshes only.
                                 //    builtOnly: use only BVHs that already exist (never stalls a frame, may miss)
                                 //    bigOnly: wide surfaces only (ground, paving, roofs)
world.groundAt(x, z, fromY, opts) // -> y | null. Highest solid surface at or below fromY (default: above everything)
world.pick(clientX, clientY)     // -> same as raycast, through the camera
world.isLoaded(x, z)             // -> true when the tiles that cover (x, z) are in the scene
world.prioritize(x, z)           // -> load the tiles that cover (x, z) next
world.updateLods(force)          // -> swap full tiles and far versions for the camera position and the tiles in memory; true when something changed
world.refit(obj)                 // -> collision boxes of the meshes under obj brought to where they are (doors.js after a leaf moves)
world.loadAll(), world.budget    // lite profile: the tile budget, and the way out of it
```

Leaf cards, glass and instanced meshes (trees, lamps) are not solid. The BVH for a mesh is built the first time a ray needs it, and near the player in idle time.

## One campus

The viewer shows one campus from one manifest, `models/main/manifest.json`. The source is still more than one `.blend` file (main campus, north campus, Sprague Library with Café Diem, and the scripted build of whole areas). They share one origin. The export (`tools/web-export/`) merges them: north campus tiles carry the `n_` prefix, and the manifest's `hide` list names main-campus ground that the north merge supersedes. The viewer removes those meshes when a tile loads. The long-term goal is one `.blend` (see [ROADMAP.md](ROADMAP.md)).

The scripted build (`blender/scripted/`) ships as `sw_` tiles. It has one folder per area: the southwest corner (Montclair Heights station surroundings, Normal Avenue, Carlisle Road, Sprague Field) the north-east district (CarParc Diem, Dinallo Heights, Machuga Heights, the Student Recreation Center, the District Energy Plant, the softball stadium and the tennis courts) the stadium district (Yogi Berra Stadium and the museum, the running track and soccer field) the west strip (Carlisle Road north with its roadside parking and the College Avenue junction beside the Red Hawk Deck) the Village west of the railway (Clove Road, Hawk Crossings, Sinatra Hall, the four Village halls and their lots) and the Overlook Corporate Center block north of the stadium district. Inside an area's footprint it owns the ground: the export step `tools/web-export/supersede.mjs` takes the other sources' ground out of their tiles there, so the viewer needs no rule for it. Its painted surfaces (road lines, stalls, the football field) carry an ordinary base colour texture through UVs; the viewer multiplies its world-space texture over it like any other surface.

Material categories come from the export as the `cat` extra on each material. Two rules were added for the southwest build and apply to every source: `turf` (artificial turf: the grass texture at a finer scale, no lawn tint, no grass tufts), and a see-through material whose category is not `glass` (chain-link, netting) stays see-through instead of becoming window glass.

`water` is the scripted build's ponds and pools (material `SW_water_*`; `cat.js` files that name as water whatever the export said). It loads no texture: `look.js` gives it a fixed dark blue-green, roughness 0.06 and a stronger sky reflection than other surfaces, and bends its normal with four fixed wave trains in world space. The ripple has no clock, so a still view is not redrawn; it fades out where a pixel spans a large part of the shortest wave. Water reflects the sky only, not buildings or trees.

Other manifest fields the viewer uses:

| Field | Use |
|---|---|
| `tiles[].lod` | Far version of a tile (`lod/`). `world.js` loads them nearest-first once the first round of tiles is in, keeps them, and swaps by distance (260 / 420 / 650 m for Low / Medium / High). A far version also stands in for its tile while the tile is not in memory, so the lite profile, which keeps the nine tiles nearest the view (two more of slack before it drops one) and every tile with no far version (8 tiles, 1.4 MB), still shows the whole campus (all far versions: 18.9 MB download, 1.5 M triangles). A far version that fails to load (or takes over 60 s) is tried again 20 s after the failure, the wait doubling with each failure up to 5 min. One timer, set for the earliest wait that is due, and one retry pass at a time serve all failed far versions, so a dropped connection does not start them all at once when it comes back (a pass started by Load everything can also take one once its wait is over). Known limit: the 60 s timeout covers a far version's own download, not the shared images and geometry the loader then fetches for it; a stalled one of those holds the retry pass until the browser gives the request up. Far versions carry no instanced trees; instead each carries stand-ins for them (scene extras `trees`, written by `tools/web-export/tree_points.mjs`: crown centre and size, trunk base, height and leaf colour per tree, `STAND_IN` in `viewer/trees-math.js`, the same record `trees.js` builds from a full tile). `scenery.js` hands them to `trees.js`, which draws them as impostors while the full tile is not in memory. Collision and picks always use the full tiles. A piece at least 4 m tall that simplifying would cut down by 1 m or more (a mast's antenna, goalposts) keeps all its triangles (`keepSkyline` in `pack.mjs`; pieces joined where their vertices meet), so the skyline stays the same at a distance. Their images are half size per side (`lod.mjs`): from 260 m a half-size paint texel is still under a screen pixel. A tile whose far version would keep 80 % or more of both its plain triangles and its draw calls, or nothing, has none (`farWorthIt` in `pack.mjs`): it would be downloaded and held in GPU memory beside the full tile for almost no saving, so the full tile draws at every distance. Trees used twice or more in a tile are instances (`tree_instance.mjs`), so they are not in the far versions; the tree stand-ins of `trees.js` show them at distance. |
| `tiles[].tex`, `tiles[].lod_tex`, `tex` | Shared files (see "Shared images" and "Shared geometry" below): the files in `tex/` and `geo/` a tile and its far version name, and the size of each. `world.js` adds each file's bytes once to the download total and to the progress when the first tile naming it is in. `total_bytes` is the full tiles plus, once each, the shared files they name. |
| `landcover` | An image draped over the 4 km skirt (`scenery.js`). |
| `far_trees` | Positions and sizes of far-field trees, drawn as simple crowns (`trees.js`): one instanced mesh per 500 m ground cell (`FAR_CELL`, `viewer/trees-math.js`), each with its own bounding sphere, so cells out of view are skipped in the view and in the shadow map. |
| `paint` | Lot markings painted into asphalt (`look.js`), up to 8 layers. |
| `source_saved`, `source_version`, `exported`, `sources` | Shown under "About this model". |

### Shared images

An image that two or more published files carry (the leaf textures are in almost every tile, a paint sheet is in its tile and its neighbours) is stored once as `models/main/tex/<hash>.webp`: the first 20 hex digits of the SHA-256 of its bytes. The tiles refer to it by a `uri` relative to their own folder (`tex/...` from a tile, `../tex/...` from a far version), as the glTF spec says; an image only one file carries stays inside it. The export does this as its last step, on the published tiles, so it needs no `.blend` (`tools/web-export/share_tex.mjs`, pure parts in `tex.mjs`; `SHARE_TEX=0` puts every image back inside its tile). It also deletes files in `tex/` that no tile names, and puts an image that is no longer shared back into its tile.

- Loading: `world.js` parses a tile with its own folder as the base (`base + dirOf(file)`), so GLTFLoader fetches `tex/` files from the right place; EXT_texture_webp reads a URI image as it reads an embedded one. A missing image fails that texture only (GLTFLoader logs it and leaves the map empty), not the tile; `check_viewer_refs.py` fails CI when a listed tile names a file that is not there.
- Memory: GLTFLoader makes a new texture per tile. `world.js` swaps it for the texture an earlier tile already has for the same file, sampler, colour space and UV transform (`viewer/texshare.js`), so the GPU holds one copy. Materials stay per tile. `free()` does not dispose a shared texture; the share disposes it with the last tile that uses it (the lite profile evicts tiles one by one). `look.js` sets only `anisotropy` on a texture, the same for every tile.
- Network: each tile still asks for the file; the browser's HTTP cache answers after the first download (GitHub Pages sends `max-age=600`, then revalidates).
- Tools that read published tiles (`supersede.mjs`, `compact.mjs`, `lod.mjs`, `tools/evidence/dump_tiles.mjs`) read the images through gltf-transform's NodeIO, which resolves the URI against the tile's folder. gltf-transform writes every image into a GLB, so `compact.mjs` and `lod.mjs` write through `keepShared` (tex.mjs), which points the unchanged shared images back at their files; the export's last step catches anything else.

### Shared geometry

Every tile carries its own copy of each tree mesh it plants (the instanced `Tree_*` meshes), byte for byte the same in up to 64 files: 38 MB of copies when this was written. The export's last step after the shared images (`tools/web-export/share_geo.mjs`, pure parts in `geoshare.mjs`; `SHARE_GEO=0` keeps everything inside the tiles) stores each compressed buffer view that two or more files carry once, in `models/main/geo/<name>.bin`. Views used by exactly the same set of files go in one pack, so a tile never downloads geometry it does not draw; a pack under 4 kB, or saving under 32 kB, stays inside its files, since every pack is one more request. gltf-transform writes the indices of many primitives into one view, so the step first gives each index accessor of such a view its own (decoded and encoded again, lossless: the viewer's loader gets the same index arrays); then a tree's indices match across tiles too. The tile's meshopt views then point at a buffer with a `uri` (`geo/...` from a tile, `../geo/...` from a far version), as the glTF spec allows; the data is copied as bytes, never decoded, so what the viewer decodes is the same.

- Loading: GLTFLoader fetches a buffer URI through its FileLoader relative to the tile's folder, as it does images. Concurrent requests for one URL wait for the first, and the HTTP cache answers the later ones. The GPU still holds one copy per tile, as before.
- Tools: gltf-transform reads such a tile but writes a GLB with one buffer only, so `build_web.sh` puts the shared geometry back into the published tiles (`share_geo.mjs --embed`) before any step reads them, and shares it again at the end. Run the same before using `compact.mjs`, `lod.mjs`, `supersede.mjs` or `drop_zero.mjs` by hand on published tiles. `check_viewer_refs.py` fails CI when a listed tile names a pack that is not there.

### Far field

What is not the campus: `skirt.glb` (the 4 km 3DEP ground), `context.glb` (campus terrain, roads and paths, the far
3DEP ground `BD_farfield_3DEP_ortho` out to 29 km, the mid-distance houses, street trees and canopy out to 10 km, and
the skyline), `n_context.glb`, `sw_context.glb`, `far_houses.glb`, `far_trees.bin` and `landcover.webp`. Three
facts set what of it can be seen. The haze (see "Haze" below) leaves 75 % of a surface's own colour at 2 km, 59 %
in red and 47 % in blue at 4 km, 30 % and 10 % at 20 km (before it, 31 % at 4 km and nothing past 10 km). The camera's far plane (`app.js`) is 33 km. The flight limit keeps the
camera within about 2.5 km of the origin. So past 10 km the ground, the ridges and the skyline show as blue-grey
shapes, and a 30 m wide building there is under 3 px wide at the walk view's 68 degrees on a 1080 px screen.

### Far view: tree canopy

Past the modelled trees, the far ground was a flat bright lawn with grey boxes on it, while the real view east from
campus is suburbs under dense tree canopy. `viewer/canopy.webp` (97 kB, 533 x 500) is the USFS Tree Canopy Cover
(NLCD, 2023, public domain), the share of each 30 m cell under tree crowns, resampled by
`tools/farview/build_canopy.py` onto 60 m cells in the model's frame over x -10 to 22 km, y -20 to 10 km (Blender):
the campus, the ridges round it and east past Manhattan (`viewer/canopy.json` records the box and source). One
texture lookup in the shaders of the far ground (the 4 km skirt, the far 3DEP ground out to 29 km, the lite profile's
flat disc) and of the far houses:

- **Ground.** Near (a pixel still sees 9 m), crowns are where two octaves of value noise at 9 m (`crownNoise`) lie
  above the noise's own `1 - cover` quantile (`NOISE_Q`, measured at every 5 %: value noise bunches round 0.5, so
  `1 - cover` itself covered 14 % for a 20 % cell), so the covered area matches the map (`tests/farview.test.mjs`);
  far, the pixel takes the cover share (`crownShare`). Crowns are a summer canopy green
  with some yellower ones; the open ground between them goes toward a grey-brown suburb mean (roofs, roads and lawn),
  more where there are fewer trees. Water (blue in the land cover map) keeps its colour: no crowns, no tint. UNVERIFIED colours, set by eye. Nothing within 150 m of the camera (the modelled
  trees are there), full from 600 m.
- **Far houses** take the canopy colour by the cover share where they stand, walls more than roofs, so they sink into
  the trees instead of standing on a lawn.
- It changes the albedo only, so it is lit, shadowed and hazed like the ground. No extra draw; the texture (97 kB)
  loads when the viewer starts, and until it has loaded (or if it fails) the ground keeps its own look.

### Haze

Every material that takes fog draws the same aerial perspective; `look.js` replaces three's fog chunks once, before
anything compiles. Pure parts and tests: `viewer/haze-math.js`.

- **How much.** The share of a surface's colour that survives a distance `d` (along the line of sight, not view
  depth, so the sides of a wide view are not clearer than its middle) is the larger of the near haze
  `exp(-(0.00027 d)^2)` (the FogExp2 the viewer had before) and the far haze
  `0.7 exp(-d / L)`, with `L` 24 km in red, 16 km in green and 10 km in blue (`HAZE`, `HAZE_RGB`); the far haze
  takes over at about 2.5 km. Blue clears
  first, so the far ground, the Palisades and the skyline turn blue-grey with distance instead of fading to one flat
  colour. UNVERIFIED: the lengths are set by eye against the standard views, for a clear day.
- **What colour.** The sky's own colour 1 degree above the horizon, toward the sun, square to it and away from it:
  three 1-pixel renders of the environment sky, read back each time the environment is baked again (the sun moved by
  more than 1.7 degrees). Drawn straight to the screen, three mixes fog after tone mapping, so the colours are tone
  mapped and encoded as the screen shows the sky. On High the scene goes to a linear target and the output pass maps
  it afterwards: there the away colour stays linear, and the fog chunk mixes after three's ACES and sRGB encoding (the
  tint toward the sun is in screen colours on every level) and undoes both (`hzOut`, `hzIn`; `acesFilmicInverse` in haze-math.js), so every quality level shows the same haze.
  The probe is half float (8 bits would clip the sky at 1); a GPU that cannot render to half float, or read it
  back (all three samples come back zero), keeps the fixed horizon colours the viewer used before (day, dusk and
  night, no tint toward the sun). The
  shader draws `away + (toward - away) * ((1 + cos a) / 2)^p`, `a` the angle between the line of sight and the sun's
  bearing, `p` fitted so that square to the sun matches too. At golden hour the haze glows toward the sun and is
  blue-grey away from it, and the far haze is never brighter than the sky behind it.
- **Cost.** A few more operations per pixel in every fogged material and no extra draw. The three values the shader
  needs (`hazeTint`, `hazeSun`, `hazeShape`) are shared by reference with every built-in material (a uniform value
  that is a plain object survives three's per-material copy of its library uniforms), so moving the sun recompiles
  nothing. A custom `ShaderMaterial` with `fog: true` would need them in its own uniforms; there is none today.
- The skyline stand-in was exported with haze painted into its colour (pale blue); `tone.js` gives it a plain grey
  (UNVERIFIED) so the haze is not counted twice.

The export applies four steps to the published files (`build_web.sh`, after supersede, before the shared images):

- `farcut.mjs`: every mesh that is not ground and lies wholly past 10 km (the New York, Jersey City and American
  Dream buildings of the main model, 148,598 triangles in six meshes) becomes one stand-in,
  `BD_skyline_silhouette_STANDIN`: a curtain along the highest elevation the source triangles reach in each 0.05
  degree of bearing, seen from the campus centre (`skyline.mjs`), flat over each bin so a slim tower keeps its
  vertical sides, kept where the outline turns by more than 0.05 degrees (700 triangles). Its tops are at the
  source's own elevation angles and distances, so it looks the same as the 3D meshes from anywhere the camera can go.
  The far plane cuts both the same way: today 70 % of the skyline's columns seen from the campus centre lie past
  20 km. `REACH=17000` (not the default) brings points past 17 km nearer along their sight lines so all of
  Manhattan shows from the campus centre; from a raised camera those points then sit lower than they should.
  It also drops the far-field filler `look.js` hides in `context.glb` (`FILLER`: the canopy carpet `WS62_crown_*`,
  its trunks and the 1,300-triangle street-tree crowns `Icosphere.001`, about 3.1 M triangles in 133,000 instances,
  never drawn because they float above the skirt): 3.3 MB that was downloaded and decoded for nothing.
- `skirt.mjs`: the skirt simplified to 5 cm (borders locked, only existing vertices kept), once (marked in extras).
- `drop_zero.mjs`: triangles of zero area in the stored positions are dropped from every tile and far version
  (3.98 M of 22.4 M when this was written, 2.75 M of them in the skirt). They draw nothing. Most come from the
  main model: the skirt's `*_skirt_under_*` geometry-node patches each subdivide the mesh again (levels 2 to 5),
  so 5.3 M of the 7.0 M evaluated triangles have an edge under 6 cm, the 16-bit position step over the skirt's
  4 km; quantized, they collapse.
- `far_thin.py`: a far tree (`far_trees.bin`) whose crown is under 4 px wide (68 degrees, 1080 px) grows to that
  width, and only the share (old radius / new radius)^2 of them stays, chosen by a hash of the position: the same
  covered area, fewer crowns (35,134 to 30,510). Fog leaves 56 % even at the skirt's corners, so none is dropped
  for fog. A second run changes nothing.

After those, `inst_filter.mjs` stores instance transforms through the meshopt filters made for them (EXPONENTIAL for
translation and scale, QUATERNION for rotation; gltf-transform filters only normals and animation). Each batch gets
the fewest bits that keep every vertex of its mesh within 1 mm of where the unfiltered transform put it, checked on
the decoded values, and records them in the node's extras (`inst_bits`) so a later rewrite re-encodes at the same
bits and the error does not add up. A rotation batch with quaternions off unit length (some shrub leaf cards: the
filter stores unit quaternions, and normalizing one moves its card by more than 1 mm) keeps its 16-bit values.

Scenery runs only when the camera moved: `scenery.js` refreshes the tree level of detail, the far versions and the grass tufts at most four times a second, then asks for one redraw and a fresh shadow map.

### Tree sway

Leaves move in the wind, in the vertex shader of every leaf material (`look.js` `sway`): no per-tree work in JS and
no extra draw. An instanced tree's crown bends by up to 1.2 cm per metre of height above the crown's lowest leaves,
in two slow beats, each tree in its own phase from its position; every leaf card also flutters 1 cm, faster. Tile
positions are quantized, so heights and offsets are worked out in metres in world space and turned back into the
mesh's own space. Plain tree
meshes (copies joined into one mesh) only flutter. The shadow map is not redrawn for it, so shadows stay still.

The clock (`look.setSway`) advances with every frame the loop draws anyway (moving, film, tour) and, while the view
is still, in an idle loop in `app.js`: a redraw 14 times a second (8 on the lite profile) that stops 2 minutes after
the last input (pointer, wheel, key, touch), while the tab is hidden, and on the lite profile when the Battery API
reports a battery at or under 20 % and not charging. Any input starts it again. A frame drawn only for the sway does
not force the screen-size cull or a new shadow map, and none is drawn while a lazy redraw is pending (tiles
streaming in on a slow GPU are still drawn in batches). With `prefers-reduced-motion` the sway is off and the idle
loop never runs; a change of that setting is followed at once. Cost: each idle frame is one full redraw of the view (on the lite profile at eye level by Susan A. Cole
Hall: 498 draw calls, 2.8 M triangles), where before a still view drew nothing.

### Trees and shrubs

What `trees.js` draws, by distance from the camera (metres; for an instanced tree, to its crown centre):

| Quality | Full tree | First middle version | Second middle version | Crown impostor | Shrub cards thinned (to the card batch's box) |
|---|---|---|---|---|---|
| Low | under 50 | 50 to 120 | 120 to 220 | 220 to 2,600 | past 35 |
| Medium | under 70 | 70 to 170 | 170 to 420 | 420 to 2,600 | past 45 |
| High | under 100 | 100 to 250 | 250 to 700 | 700 to 2,600 | past 60 |

Tile far versions (`world.js`, 260 / 420 / 650 m) and the screen-size cull (`look.js`) apply as before. The numbers are
`DIST` in `trees.js` and `TREE_MID`, `TREE_FAR_MID`, `SHRUB_REACH` in `viewer/treelod-math.js`.

- **Middle versions.** Most bark triangles are twigs, and a twig costs as many triangles as a limb. Each bark mesh is
  split into pieces (triangles joined by a shared vertex position) and its index reordered once: pieces at least 6 cm
  thick (`BARK_MIN_DIAMETER`, estimated as area / (pi x length), at the largest scale the mesh is drawn at) first, then
  thinner pieces from the largest area to the smallest. The first middle version leaves out the smallest thin pieces
  that together hold at most 10 % of the bark's area, the second every thin piece; leaves stay whole in both. A
  middle version is the same vertex and index buffers drawn over a shorter range: an instanced mesh beside the full
  one for instanced trees, the draw range itself for plain tree meshes (`Tree_*`, a tree used once in its tile or
  copies joined into one mesh; collision is not affected: their BVH is built again on the new order). No download
  and no extra GPU geometry. The reordering runs in idle time after a tile arrives (about 3 s of work for the whole
  campus on a desktop CPU); until a group is done its trees draw in full.
- **What changes on screen.** A 6 cm branch at the first middle distance is 0.51 px wide at Medium in the walk view
  (68 degrees, 1280 x 800; 0.74 px in the orbit view's 50 degrees). Antialiasing still shows such a branch as a faint
  line, so the first step is also limited by area. Measured by rasterizing single trees from the tiles (unlit, sky
  behind, 4 x 4 samples per pixel), the first middle version changes a tree's pixels by 0.1 to 1.4 / 255 on average
  (the honey locust, the sparsest crown, is the largest; under 1 % of its pixels change by more than 24 / 255), the
  second by 0.4 to 3.3 / 255 (honey locust: 2.7 / 255 after a 3 x 3 blur, no pixel over 24 / 255 after it).
- **Shrubs.** A shrub is a core and thousands of instanced leaf cards of about 2 x 5 cm (876,000 cards in 12 batches
  on the sw16 tiles), drawn whole at any distance before. Past the reach one card in 8 is drawn (`thinPick`, a hash of
  the index), grown by the square root of 8 about its own origin: the same covered area from an eighth of the cards.
  At 45 m a full card is 0.28 x 0.61 px in the walk view, a grown one 0.8 x 1.7 px. The shrub's mean colour and
  covered area stay the same (rasterized: 111.7 to 111.8 / 255 red, 209 to 210 px at 45 m); its speckle changes.

## Night sky

What the sky shows after sunset, for the date and time chosen under Sunlight. Nothing here runs per frame except
following the camera; a still view is not redrawn.

- **Stars** (`viewer/sky.js`, `viewer/sky-math.js`). The 892 stars of the Yale Bright Star Catalogue brighter than
  magnitude 4.5 (`viewer/stars.json`, 24 kB, 10 kB compressed), at their J2000 positions turned to the campus horizon
  by the sidereal time (IAU 1982; precession since 2000, about 0.3 degrees, is left out). One `Points` draw on a
  sphere 31 km out, inside the camera's far plane, so buildings and ridges hide them. Brightness follows the
  magnitude scale, compressed (`starBrightness`), colour follows B-V (`starColor`, kept pale). They fade in from
  the end of civil twilight to nautical dusk (sun 4 to 12 degrees down), and out toward the horizon where haze and
  the region's lights hide them. The file loads the first time stars are due, so a daytime visit never fetches it.
- **Moon.** Its position from the low-precision series of the Astronomical Almanac (about 0.3 degrees), corrected for
  parallax (up to 1 degree from the campus). It is drawn at its real angular size (0.52 degrees) as a disc facing the
  camera and lit from the sun's real direction, so its phase and the side it is lit from are right without a phase
  formula. Its dark patches are a rough sketch of the maria (UNVERIFIED shapes). By day only its lit part shows,
  pale. It brightens the night sky with its lit fraction (`look.setMoon`).
- **Light dome** (`look.js`, the sky shader). The night sky over Montclair is never black: a warm glow low in every
  direction over a dark blue zenith, in two peaks with a dip between (`domeShape` in `viewer/sky-math.js`): a broad
  glow and a bright core toward Midtown Manhattan (bearing 124 degrees), a weaker core over Newark and its airport (168
  degrees), standing higher over the cities. UNVERIFIED colours and
  strengths, set by eye. The environment sky has it too, so night reflections and the haze colour follow.
- **City lights.** The far houses (`far_houses.glb`, the house proxies in `context.glb`) light windows on their walls
  (3 m bays, 2.8 m storeys) one by one as it gets dark, up to one in four, from the sun 2 degrees up to 6 down. The
  skyline stand-in has windows in cells of about a pixel (0.04 degrees of bearing by 12 m) grouped in towers of 0.15
  degrees (50 m at 20 km), each tower lit more or less and its windows warm or cool; where a pixel covers many cells
  it takes their mean, so the speckle does not flicker and the towers' differences stay. Which windows are lit is a
  hash of position, as for the fake rooms behind campus windows: a pattern, not data. The materials' own shaders,
  no extra draw.
- **Tower tops.** The Empire State Building, One World Trade Center and the Chrysler Building (`LANDMARKS` in
  `viewer/farview-math.js`) get a lit top: one sprite each at the highest point of the skyline stand-in along the
  landmark's bearing (`towerTop`), shown with the city lights. One draw. UNVERIFIED colours (the Empire State
  Building's change for events).
- **Sunset glint.** With the sun under 10 degrees and west of the campus, one tower in three in the skyline blazes
  in the sun's colour, in window rows that fade to their mean where a pixel spans several. UNVERIFIED: the stand-in
  is a curtain with no facades, so which towers glint is a hash of bearing, not data; it stands for the west-facing
  glass of Manhattan that mirrors a low western sun toward New Jersey.

## Film

`viewer/cinema.js` (Film, key N) plays the fixed shots of `viewer/cinema-math.js`: the campus from the south-east,
the hilltop view toward Manhattan, eye level by Susan A. Cole Hall (all 35 minutes before the real sunset of the
date shown) and the skyline 100 minutes after sunset. Each shot is an eased move (smootherstep, starting and ending
at rest) from one pose to another in orbit mode, so every target sits below its camera and every camera inside the
flight limit (`tests/cinema.test.mjs` checks both). At each cut the view fades to black, the tiles under the next
shot are asked for first (up to 5 s), the light changes and the caption names the place. The letterbox bars (2.39:1),
the fade and the caption are page elements, so the mode adds nothing to draw; the only cost is the light change at a
cut (one environment bake). The skyline shots keep their targets 120 m ahead of the camera, and each cut asks for
the tiles under the camera and the target first: the lite profile keeps the nine tiles nearest the orbit target, so
a far target would let the foreground go. With `prefers-reduced-motion` each shot holds its last
pose. Any input on the view, Esc, the Stop button, or a camera move another module asks for stops it and gives back
the pose, the navigation mode (fly looks from the old camera; walk stands where the walker stood), the light
and the panel. A mode key (2, 3) during the film stops it too and leaves the view to that mode. Started while
a walk is still landing, the film waits for it (input on the view, Esc or another camera move cancels the wait). A
shot whose ground tiles were not all in at the cut starts on whatever surface is there (else the campus floor) and
eases to the real ground over about a second when they arrive (checked four times a second); a held shot under
reduced motion keeps its pose.

## Moving to a place

Search results, place labels, the landmark hunt and the guided tour fly to a place through `app.placePose` and `app.flyTo(pose, { land: true })`; the minimap keeps the current camera offset and lands too. The first guess of the ground uses collision that is already built (it never stalls a frame), else the full lookup where the tiles are in, else the campus floor (`bounds.min.y + 20`; far-field ground wider than 1 km does not count toward `bounds`, `inCampusBox`: the north model's `BD_farfield_3DEP_ortho` reaches y -54 and had put that floor 150 m underground). That guess is often wrong: far from the view the collision is not built and the tiles may not be in, and before this rule a camera framed on the floor fallback could end under a hill or a roof. On arrival the landing step waits for the tiles under the target and the camera, builds their collision, and applies `landPose` (`viewer/pose-math.js`): a target off the ground moves to the highest surface there and the camera moves with it; a camera less than `CLEARANCE` (3 m) above the highest surface under it is lifted. A new move cancels it. Permalinks, the overview and the top view are poses, not places: they are not landed.

## Follow me

In walk mode the "Use my location" button (top left) lets the phone drive the walker (`viewer/follow.js`). It reads `navigator.geolocation.watchPosition` (high accuracy) and the compass. **The position stays on the device:** nothing stores, logs or sends it; the button says so. From the first fix until the view moves to a place (any `fly` event: search, overview, a share link), the address bar holds no view (`app.follow.private`), so a copied link or the browser history cannot carry the user's position; Share says the link leaves it out.

- **Position.** Each fix goes through `latLonToLocal` (`geo.js`) into a constant-velocity Kalman filter (`createTrack` in `follow-math.js`, the fix's accuracy as its noise), so a ±5 m jitter does not shake the view. The first fix uses `player.teleport` (waits for the tiles there); after that `player.guide` holds the filtered point and walk mode eases toward it (rate 3/s) with no wall collision, since GPS crosses what the model gets wrong. The eye stays 1.65 m over the surface under the walker (a ground ray from 1.5 m above the feet). A fix with accuracy worse than 80 m is not used. A fix more than 150 m outside the campus tiles leaves the walker where they are and says how far away the user is. A blue ring on the ground shows the accuracy radius.
- **Heading.** Held up, the view looks where the back of the phone points; held flat, where its top edge points (`phoneView`: the W3C rotation matrix of alpha, beta, gamma). Pitch follows the tilt (-60 to 45 degrees). Android sends `deviceorientationabsolute` (alpha from north); iOS sends a relative alpha plus `webkitCompassHeading`, so the offset between them is learned and eased, only while the phone is clearly flat or clearly upright. Both report magnetic north; `DECLINATION` (-12.4 degrees, WMM2025 for the campus in late 2026) turns it into true north, then the grid convergence into the viewer's yaw. Heading eases at 10/s, half that for turns under 1.5 degrees, so a still phone does not shimmer. iOS asks for motion access only from a tap (`DeviceOrientationEvent.requestPermission` runs first in the button handler). With no compass the user turns by dragging as usual.
- Tapping the button again, or leaving walk mode, stops it, clears the watch and cancels a placement still waiting for its tiles; a stop while the iOS motion prompt is open wins over the prompt's answer. The first fix stands the walker on the lowest surface there (the ground or the ground floor), not on a roof.

## Path network

`viewer/paths.json` is the graph walking directions route on. `python3 tools/places/build_paths.py --cache DIR` builds it from the same OSM API calls and cache as `build_places.py`: footways, paths, pedestrian ways, steps and crossings, and streets at a cost (motorways, trunks, private and `foot=no` ways left out), split at shared nodes (two ways between the same junctions both stay, such as stairs beside a ramp), clipped to the campus tiles, shapes simplified to 0.6 m, and pieces under 60 m long in total dropped. Ways marked indoor, corridors, ways on another level, and any stretch that runs inside a building outline or crosses one of its walls, multipolygon buildings and their courtyards included (unless OSM maps it as a passage through the building) are left out, so a route never goes inside a building: it ends at the entrance (AGENTS.md rule 16 for housing).

- `nodes`: flat `[x0, z0, x1, z1, ...]`, 0.1 m, in the frame of `places.json`.
- `edges`: `[a, b, flags, grade]`. Flags: 1 steps, 2 steep, 4 street, 8 crossing. `grade` is the steepest 20 m stretch along the OSM edge in percent (end to end for an edge under 20 m, and over the last 20 m before its end; under 2 m is level), from the USGS 3DEP 1 m bare-earth DEM sampled every 10 m (0 on bridges and tunnels, where the DEM is not the walking surface; -1 where the DEM gave no height, which is unknown, not level). Only a complete DEM answer is cached; a failed, partial or unreadable one is tried three times, then those heights are unknown. Steeper than 8.33 % (1:12, the ADA ramp limit) sets the steep flag. A DEM cell on a wall or kerb can still read steep: the grade is evidence, not a survey.
- `entrances`: `{ osm, node, mapped }` for each building in `places.json` the graph reaches. OSM maps no entrances on the campus yet (Nov. 2026), so every one is `mapped: false`: a footway dead end within 6 m of the outline, or a path point within 3 m of it, else the nearest point on a path within 25 m, which splits that edge (UNVERIFIED). An `entrance=*` node on the outline in OSM replaces the guesses for that building the next time the file is built.

## Walking directions

In walk mode "Go to a place" (under "Use my location") opens a search over `app.places` (`searchPlaces`). Choosing a place routes from the walker: the GPS point when follow me is on (`player.guide`), else where they stand. `route-math.js` snaps the start onto the nearest usable edge within 120 m (part way along it), then runs A* to the place's entrances from `paths.json` (a place with none, such as a lot or a field, ends at the nearest path point). Streets count 1.25 times their length, so a footway is preferred where one runs alongside. The step-free box leaves out steps and steep edges; if nothing is left, it says there is no step-free route on the path map. The card gives the walk in metres and minutes at 1.3 m/s, and says when the entrance is guessed (UNVERIFIED), when the route has stairs or steep stretches. The route line is drawn on the ground every 3 m at the surface under it and redrawn as tiles arrive. The graph is fetched the first time the picker opens (29 kB gzipped). Leaving walk mode clears the route.

## Flight limit

The camera can fly well beyond the campus but not out to the far stand-ins (the city skyline silhouettes read right only from the campus). `viewer/flight-math.js` derives the limit from the manifest: the box of the campus tiles grown by `MARGIN` (1000 m) sideways, cut back to `SKIRT_INSET` (150 m) inside the far-field skirt (`landcover.half`, 2000 m from the origin, so its edge does not come into view at the side; today this cuts the north side to 410 m past the tiles), and a ceiling `CEILING_SPAN` (1.25) campus spans over the campus floor, above the top view (1.05 spans). Today: x -1640..1480, z -1850..1480, ceiling about 2400 m over the floor. In fly mode the outward part of the velocity slows over the last `SOFT` (250 m) before the limit, so the camera eases to a stop and slides along the limit; motion back toward the campus is never slowed. Everything else (orbit zoom and pan, eased moves, share links that point outside) is clamped to the limit each frame. Walk mode needs ground, so it needs no tighter limit.

## Interiors

Most buildings are shells: their windows show fake rooms (interior mapping in `look.js`), and small meshes are hidden by the screen-size cull (a mesh is drawn while its radius is more than distance × 0.02 / 0.008 / 0.003 for Low / Medium / High). A building with a real interior (the scripted College of Communication and Media, floors 1 and 2) is listed in `viewer/rooms.json`, and inside it the viewer works differently:

- **Volumes.** `volumes[]`: `{ id, building, short, ring: [[x, z], ...], y0, y1, ceiling, levels: [{ floor, y }], unverified: [...] }` in viewer metres. The ring is the floor outline of the interior plan; `y0` is its lowest floor, `y1` the top of the shell that holds it; `levels` are the floor heights.
- **Culling.** While the camera is inside a volume or within 40 m of it (`INTERIOR_REACH`), meshes whose centre lies in the volume grown by 1 m are not screen-size culled, so partitions and furniture stay drawn. Everything else is culled as before. The rule is checked in the same cull pass as the size rule (at most five times a second while the camera moves, and once when it stops), so the view still draws on demand.
- **Glass.** A glass mesh whose box reaches into a volume (grown by 1 m) gets a copy of its material. Per pixel, vertical glass inside the grown volume has no fake rooms; clear glazing (`isClearGlass` in `cat.js`: not a screen, lens, frosted, dark or opal glass) is drawn see-through from both sides, with its slight tint and a sky reflection that grows at grazing angles (Schlick Fresnel), and such meshes cast no shadow, so sunlight comes in. The test is per pixel because the export joins meshes by material across buildings; the volumes reach the shader through a float texture (see "Volumes in the shaders" below).
- **Volumes in the shaders.** The glass and interior-light shaders read every volume from one float texture (`packVolumes` in `rooms-math.js`: rows of 256 texels holding each volume's ring range and heights, its grown box, its ceiling, then all ring points), so up to 256 volumes with any number of ring points reach the shaders. Per pixel, each volume is tested by its box first, and only a volume whose box holds the pixel runs the ring test.
- **Interior light.** Inside a volume a room gets only sky and hemisphere light, so ceilings took the dark ground colour and walls sat in shade. Each material of a mesh that reaches into a volume gets a copy whose shader adds an even warm-white indirect light (`INTERIOR_LIGHT` 0.6 in `look.js`, colour 1, 0.95, 0.86) to every pixel that `interiorLit` accepts: inside the outline and more than `EDGE` (0.2 m) from it (so the shell's outer face is not lit), from 0.3 m under the lowest floor to the top of the shell (in its top half metre only surfaces facing down: the underside of a flat roof is lit, the parapets are not), and not a surface facing up above the interior `ceiling` (the roof). Ceilings take all of it, walls 0.8, floors 0.55 (`ambientFactor`), so floors keep their colour. The sun still comes in through see-through glass, with its shadows. The light is electric: the same by day and by night, so after dark a building with rooms reads as lit from inside through its windows. No light objects and no extra draw calls: only the shader of those materials changes. `rooms.json` volumes carry `ceiling`, the highest interior ceiling.
- **Instanced window units.** Glass in an instanced mesh has no shader hook (`decorate` leaves it at 82 % opacity), so the carried-over window units of the north wing read as dark panes. A unit set whose box centre lies in a volume grown by 1 m gets clear glass instead: 22 % opacity, both sides, no shadow.
- **Doors.** Entrance doors open in walk mode (`viewer/doors.js`, pure parts in `doors-math.js`; #119). The build marks each moving leaf as a node named `DOOR_<building>_<entrance>_<leaf>` with extras `door` in Blender world axes: `{ id, building, kind: 'swing' | 'slide', hinge, axis, open (degrees) | travel }`. Leaves with the same `id` move together. A door opens over 0.6 s for a walker within 3 m who faces it (within 70 degrees) and closes once the walker is 4.5 m away. Outside walk mode every door is shut. A door open past 60 % does not collide (`world.js` skips meshes with `userData.doorOpen` in `pushOut` and `raycast`); while it moves, `world.refit` keeps its leaves' collision boxes where the leaves are. Nothing runs until a loaded tile has a door leaf.
- **Collision.** Glass is not solid (`world.js`), so a walker passes through glass doors and also through a glass wall or balustrade. That is left as it is.
- **Walk mode.** Floors above ground work: the ground ray follows the slab you stand on and steps up stairs of up to 0.5 m a step. Walk mode started from fly mode stands you on the storey under the camera (`walkStartY`), not on the roof. A stair core the plan models as a closed block cannot be entered.
- **Room labels.** `rooms[]`: `{ name, x, z, y, floor, building, unverified }`, `y` the floor height. `labels.js` puts each number 2.1 m above its floor (no ground lookup) and shows it only within 20 m, only for the floor the camera is on (from the camera height against `levels`: the highest floor at least 0.5 m below it), and only in walk mode or while the camera is inside the volume. Of those, a label shows only when a ray from the camera to its label point reaches it without hitting solid collision first (`sightPass`: at most 12 rays a label pass, rooms never checked first, only when the camera moved, on collision already built), and the room the camera stands in always shows (`roomHere`: the nearest room point on its floor within 5 m, inside the volume). Glass is not solid, so rooms behind glass show. Room labels take part in the same declutter as place names, ahead of them; while the camera is inside a volume, place names are hidden (unless one was just chosen), since they would show through the walls and roof. Their tooltip says the position is UNVERIFIED (read off an evacuation plan).
- **Search.** A query with a digit also searches the rooms, as `CCOM 2007` (the building's `short` name, else its full name) with the alternative names `Room 2007` and `2007`. Choosing one glides to eye height on its floor and starts walk mode there.
- **The file.** `python3 tools/places/build_rooms.py` writes `viewer/rooms.json` from every `blender/scripted/<area>/interior.json`, through the plan's own label rule (`blender/scripted/rooms.py` `labels`), without Blender. The building name is the place from `places.json` inside the outline; its short name comes from `SHORT` in the builder. Run it again when an interior plan changes; `tests/py/test_build_rooms.py` checks that every room of the published file lies inside its volume.

## Testing

- `node --test` runs the unit tests in `tests/` for the pure modules. CI runs it in the `viewer` job.
- `node tools/viewer-test/smoke.mjs` serves the checkout, opens the viewer in headless Chromium, loads a few tiles, exercises each mode and tool, and fails on any console error. It is optional and not part of CI. Each step waits for its condition, not for a fixed time, because software WebGL can take seconds per frame; a full run then takes 20 minutes or more.
- `node tools/viewer-test/shoot.mjs <outdir>` takes the standard views for before/after comparison.
- URL switches for testing: `?quality=low|medium|high`, `?lite=1|0` (force the phone profile on or off), `?tiles=N` (load only the N nearest tiles), `?capture` (keep the drawing buffer for screenshots), `?interiors=0` (leave `rooms.json` out: no interior rule, no room labels).
